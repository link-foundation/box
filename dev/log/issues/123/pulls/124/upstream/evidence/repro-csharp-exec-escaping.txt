### reading
###
### The payload ran twice -- once while building the commit message and once
### while building the tag message -- and the stub git shows
###   git commit -m chore: release v0.3.17
### with the description already consumed by the shell before git saw it, which
### is also why the release commit silently loses the description an operator
### typed.
###
### This is NOT closed by the workflow-level fix in report D. Reading the input
### through `env:` stops the *runner* from pasting it into the step's script; the
### value still arrives on the script's argv and is still concatenated into a
### command string here. Both fixes are needed, and this one is the cheaper of
### the two: execFileSync('git', ['commit', '-m', commitMsg]) passes the message
### as one argument and needs no escaping at all.
###
### Reachability: --description is supplied by the operator dispatching
### release.yml (release.yml:617). In changeset mode the descriptions parsed out
### of changeset files do not reach commitMsg -- version-and-commit.mjs:336-358
### writes them to CHANGELOG.md and builds the commit message from the version
### alone -- so a pull request author cannot reach this site. That makes it an
### operator-reachable defect rather than a contributor-reachable one, the same
### standing as report D.
###
### Across the other six templates the same construction is either fed no
### untrusted text (js, go, java -- their message is derived from the version) or
### uses an argv form that cannot be injected at all (rust, python, php). Only
### csharp combines a command string with operator-supplied text, so this report
### goes to csharp alone. java is worth a footnote: its commit line has no
### escaping whatsoever, so it is one edit -- a message that carries text -- away
### from the same defect.
