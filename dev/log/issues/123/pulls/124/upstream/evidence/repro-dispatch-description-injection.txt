### Two payloads per interpolating block, because the context decides the answer:
###   cmdsub   `$(...)` alone -- reaches only interpolations that sit where the
###            shell performs expansion.
###   heredoc  a newline, a line reading `EOF`, then `$(...)` -- what it takes to
###            escape a *quoted* heredoc (`cat > f << 'EOF'`), inside which the
###            shell expands nothing. See probe-dispatch-input-newline.txt for
###            what is and is not established about delivering a newline.
###

### reading, site by site
###
### Which input reaches the site matters: in all three templates `bump_type` is a
### `choice` and GitHub validates it against `options` (422, no run -- measured in
### probe-dispatch-input-newline.txt), while `description` is `type: string` and
### is validated by nothing. A site that interpolates only `bump_type` is defence
### in depth; a site that interpolates `description` is live.

  csharp release.yml:613  `--bump-type "${{ ...bump_type }}" --description
                          "${{ ...description }}"`, an inline command line. Inside
                          double quotes `$( )` still expands, so this is LIVE
                          through `description`.
  csharp release.yml:759  `cat > "$CHANGESET_FILE" << 'EOF'` with both inputs in
                          the body: the shell expands nothing there, so `$( )`
                          alone is inert. It becomes execution only with a
                          newline plus a line reading `EOF`. Without a newline it
                          is still content injection into the changeset the
                          release then commits and prints (report C).
  go     release.yml:281  inline command line; `--bump-type` is additionally
                          unquoted, and `--description "${{ ... }}"` makes it
                          LIVE.
  java   release.yml:382  inline command line, `--bump-type ${{ inputs.bump_type }}`
                          unquoted. Only the validated `choice` reaches it, so
                          this one is defence in depth rather than live.
  java   release.yml:429  `DESCRIPTION="${{ inputs.description }}"` in a `run: |`
                          block, with `--bump-type "${{ inputs.bump_type }}"`
                          below it: LIVE through `description`.
  js, python, php         no dispatch input reaches a `run:` script.
  rust                    likewise: it reads both inputs through `env:` at
                          release.yml:1163-1167 and references `"$BUMP_TYPE"` /
                          `"$DESCRIPTION"`, which is exactly the fix the four
                          sites above need.

### layer 2, read separately
###
### The C# template's scripts/version-and-commit.mjs is a second, independent
### defect at the same input: exec() at :69-74 calls execSync(command), which runs
### the string through /bin/sh -c, and the two call sites build that string with
### `${commitMsg.replace(/"/g, '\"')}` (:409-412) and the same shape for the tag
### message (:419). Escaping the double quote leaves `$( )` and backticks intact,
### so the payload ran twice in the transcript above -- 16 bytes for two eight-byte
### markers -- and the stub git received `git commit -m chore: release v0.3.17`
### with the description already consumed.
###
### This one is NOT closed by the workflow env: fix reports D suggest: the value
### still arrives on argv and is still concatenated into a command string. It is
### reported separately (report E) with execFileSync as the fix.
